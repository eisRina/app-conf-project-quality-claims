
# Правила работы в команде

## Git-стратегия

Стратегия ветвления выбирается на воркшопе №2 и фиксируется в ADR 001.
До этого: ветки `feature/<кратко>` создаются от `main`, изменения попадают в `main` только через Pull Request.

### Ветвление
- `main` — стабильная версия
- `feature/<кратко>` — новые функции и документация
- `bugfix/<кратко>` — исправление ошибок

### Коммиты
Используем [Conventional Commits](https://www.conventionalcommits.org/):
- `feat:` новая функция
- `fix:` исправление бага
- `docs:` изменения в документации
- `style:` форматирование кода
- `refactor:` рефакторинг
- `test:` добавление тестов
- `chore:` рутинные задачи

Пример: `feat: add user authentication endpoint`

## Code Review

- Каждый PR требует минимум 1 approval от другого участника команды
- Ревьюер проверяет: стиль кода, архитектуру, наличие тестов
- Автор отвечает на все комментарии в PR

## Встречи команды

- Частота: 2 раза в неделю
- Канал связи: Telegram
- Время ответа на сообщения: в течение 24 часов

## Разрешение конфликтов

1. Обсуждение в команде
2. Голосование (большинство голосов)
3. Если не можем решить — обращаемся к преподавателю

## Правила Pull Request и защиты ветки main

### Стратегия ветвления

Команда использует GitHub Flow. Решение описано в ADR 001:
`docs/adr/001-branching-strategy.md`.

Основная ветка `main` должна содержать стабильную версию приложения.

Все изменения выполняются в отдельных ветках:
- `feature/<название>` — новая функциональность;
- `bugfix/<название>` — исправление ошибок;
- `docs/<название>` — изменения документации.

### Создание Pull Request

1. Создать новую ветку от актуальной `main`.
2. Внести изменения и выполнить локальную проверку.
3. Создать коммит с использованием Conventional Commits.
4. Отправить ветку на GitHub.
5. Открыть Pull Request в `main`.
6. Заполнить шаблон `.github/pull_request_template.md`.
7. Назначить другого участника команды рецензентом.
8. Получить минимум одно одобрение (Approve).
9. Разрешить все обсуждения перед объединением.
10. После успешного Merge удалить рабочую ветку.

### Защита основной ветки

Для ветки `main` создан активный GitHub Ruleset `protect-main`.

Установлены следующие ограничения:
- Прямой push в `main` запрещён.
- Изменения принимаются только через Pull Request.
- Требуется минимум одно одобрение другого участника.
- При добавлении новых коммитов предыдущие одобрения сбрасываются.
- Все обсуждения должны быть разрешены до Merge.
- Удаление ветки `main` запрещено.
- Принудительный push (`git push --force`) запрещён.
- Список обхода правил (Bypass list) пуст.

Работоспособность защиты проверена командами
`git push origin main` и `git push --force origin main`.
Обе операции были отклонены GitHub с ошибкой GH013.

### Проверка изменений

Перед одобрением Pull Request рецензент проверяет:
- Соответствие изменений поставленной задаче.
- Отсутствие секретных данных и служебных файлов.
- Корректность работы приложения FastAPI.
- Работу эндпоинта `GET /health`, если изменения затрагивают приложение.
- Актуальность документации.
- Отсутствие неразрешённых конфликтов.

После успешной проверки рецензент выбирает
`Review changes → Approve → Submit review`.

### Разрешение конфликтов

Если при объединении веток возникает конфликт:

1. Определить файлы с конфликтующими изменениями.
2. Сравнить изменения обеих веток.
3. Сохранить необходимые изменения каждого участника.
4. Удалить служебные маркеры конфликта.
5. Проверить итоговое содержимое файлов.
6. Создать коммит с разрешением конфликта.
7. Повторно проверить Pull Request перед Merge.
