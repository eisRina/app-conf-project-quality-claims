
# ADR 001: Выбор стратегии ветвления Git

## Статус

Предложено

## Дата

- @samsonow-Star — разработчик, участник Code Review

## Контекст

Наша команда Quality Claims разрабатывает систему регистрации и обработки претензий по качеству продукции в рамках курса «Управление конфигурацией бизнес-приложений».

Характеристики проекта:

- Размер команды: 2 человека.
- Длительность проекта: 16 недель (1 семестр).
- Частота релизов: промежуточные версии по мере выполнения практических работ и финальный релиз в конце семестра.
- Уровень опыта команды с Git: начальный, участники осваивают ветвление, Pull Requests и Code Review.
- Требования к стабильности `main`: высокие, поскольку проект проверяется преподавателем и другими командами.

Необходимо выбрать стратегию, которая позволит:

1. Параллельно работать над функциональностью.
2. Сохранять стабильность основной ветки.
3. Выполнять требования курса по Pull Requests и Code Review.
4. Минимизировать сложность процесса для двух участников.

## Рассмотренные варианты

### Вариант A: GitFlow

GitFlow использует отдельные ветки `main`, `develop`, `feature`, `release` и `hotfix`. Функции объединяются в `develop`, а готовые релизы переносятся в `main`.

Плюсы:
- Чёткое разделение разработки и выпусков.
- Удобное управление несколькими версиями продукта.

Минусы:
- Сложная структура веток для небольшой команды.
- Дополнительные слияния увеличивают риск конфликтов.

Подходит ли нам: Нет. Для учебного проекта из двух человек стратегия избыточна.

### Вариант B: GitHub Flow

GitHub Flow предполагает стабильную ветку `main`. Все изменения разрабатываются в отдельных короткоживущих ветках и попадают в `main` через Pull Request после проверки.

Плюсы:
- Простая структура и понятный порядок действий.
- Удобное командное ревью и быстрое объединение изменений.
- Соответствие требованиям курса по PR и approval.

Минусы:
- Отсутствует отдельная интеграционная ветка.
- Задержки Code Review могут замедлять разработку.

Подходит ли нам: Да. Стратегия соответствует размеру команды и требованиям преподавателя.

### Вариант C: Trunk-Based Development

Разработчики часто интегрируют небольшие изменения в основную ветку, используя короткоживущие ветки и при необходимости feature flags.

Плюсы:
- Частая интеграция снижает вероятность крупных конфликтов.
- Подходит для непрерывной интеграции и развёртывания.

Минусы:
- Требует развитой автоматизации тестирования.
- Недостаточно проверенные изменения могут нарушить стабильность основной ветки.

Подходит ли нам: С оговорками. Автоматизированные тесты и CI пока не настроены.

## Решение

Мы выбрали стратегию **GitHub Flow**.

Схема ветвления:

```text
main             A────────B────────C
                  \      / \      /
feature/claims     D────E   \    /
                            \  /
feature/version              F─G
```

Каждая новая ветка создаётся от актуальной `main`, а после проверки её изменения объединяются обратно через Pull Request.

Правила работы с ветками:

1. `main` содержит проверенную рабочую версию приложения.
2. Новая функциональность создаётся в ветках `feature/название`.
3. Исправления выполняются в ветках `bugfix/название`.
4. Изменения документации выполняются в ветках `docs/название`.
5. Для объединения изменений в `main` необходим Pull Request и минимум одно одобрение другого участника.
6. Коммиты оформляются по Conventional Commits: `feat:`, `fix:`, `docs:`, `chore:`, `test:`.
7. После успешного слияния рабочая ветка удаляется.
8. Планируется ruleset `protect-main`: запрет прямого push, force-push и удаления `main`; обязательное одобрение PR; сброс устаревших одобрений и закрытие обсуждений до merge.
9. Обязательные CI-проверки будут добавлены после настройки CI в практике №5.

## Обоснование решения

1. **Размер команды.** Для двух разработчиков GitHub Flow обеспечивает необходимое разделение работ без дополнительной ветки `develop`.
2. **Частота релизов.** Изменения можно объединять после завершения каждой небольшой задачи.
3. **Опыт команды.** Участники уже применяли отдельные ветки и Pull Requests на практике №1.
4. **Требования DoD.** Стратегия поддерживает обязательное ревью и контролируемое объединение изменений.

## Последствия

### Положительные (+)

- Упрощается управление ветками.
- Каждый участник может независимо выполнять задачу.
- История изменений сохраняется через Pull Requests.
- Снижается сложность подготовки релизов.

### Отрицательные (-)

- Нет отдельной ветки для интеграционного тестирования.
- Работа может задерживаться при отсутствии ревьюера.
- Без автоматизированных тестов часть ошибок может попасть в `main`.

## Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Конфликты при объединении веток | Средняя | Среднее | Делить задачи на небольшие PR и регулярно обновлять ветки |
| Нестабильный код попадёт в `main` | Средняя | Высокое | Проверять PR, запускать приложение и тестировать `/health` перед approval |
| Второй участник недоступен для ревью | Средняя | Среднее | Договориться об ответе в течение 24 часов, при длительной задержке согласовать действия с преподавателем |
| Единственный владелец репозитория может менять настройки защиты | Средняя | Высокое | Документировать настройки в `CONTRIBUTING.md` и согласовывать изменения с командой |
